# VDA5050 open items (2026-10-09)

## 1. Confirmed decisions

- **Last-node tolerance:** the robot counts its final position reached at 0.35-0.45 m and cannot honour a tighter `allowedDeviationXY` yet. The server sends 0.35 m for the last node (`ROUTE_DEVIATION_XY_FINAL_M=0.35`). A waypoint value of the legacy 0.1 still reads as unset and maps to this value. Precision for nodes with actions comes from the action (e.g. dock), not from the node tolerance.
- **corridorWidth is per side:** `corridorWidth: 1.0` means a 2 m wide band (1 m each side of the edge).
- **Skip semantics (robot team reply):**
  - a) `skippable: true` without `corridorWidth` is treated as no skip. We always send both together.
  - b) A skip is reported as errorType `nodeSkipped`, errorLevel WARNING, errorReferences nodeId. It is not a block and must not fail or pause the mission.
  - c) A skip never happens on the start node or the last node, and never on two consecutive nodes.
  - d) `maxWaitS` counts from the first blocked verdict.
- **nodePolicy rollout:** `VDA5050_NODE_POLICY_MODE=off` in `.env.example` until the robot team confirms their nodePolicy release (otherwise the action is reported FAILED "Action handler not found"). Then switch to `factsheet` (or `on`). Phase 1: `maxWaitS` 10, `skippable` false. The code default is unchanged (`factsheet`).

## 2a. Order-ready gate (implemented)

A new orderId goes out only once the robot's state shows the previous dispatcher order done
(`nodeStates` and `edgeStates` empty). Seen in 2 of 4 successful orders: a single-node mission
completes on the robot's `missionStatus` flag, the next mission's order went out at once, and
the old order's final node was never reported.

- Gate: `Robot._send_order` (new-order branch). The send stays owed (`_pending_send`) and the
  next state message retries it; it counts no order mismatch.
- Not held: a resend of the same orderId, the robot's own offline order, an order the robot
  reported failed or cancelled, and an order released from the wait: one it kept after a
  cancelOrder to drop it went unanswered, or one the dispatcher replaced with a new revision.
- A robot that keeps listing the old order's nodes, is not driving, and has stayed so for
  `Robot.ORDER_CLEAR_DWELL_S` (10 s) gets one `cancelOrder` (purpose CLEAR) per dwell; the owed
  send follows. A driving robot is waited for, bounded by the mission timeout.
- Diagnostic: a node completed by the robot's flag before its `lastNodeSequenceId` reached the
  order's final node is logged (WARNING) and recorded as `MISSION.NODE_NOTE`
  (`info_type completedWithoutFinalNode`), once per order.
- To verify on the robot: a fleet-recorder capture of one full order, to see whether `nodeStates`
  empties with the final `lastNodeId`. If it empties before it, the gate does not close the
  race and the next order must also wait for `lastNodeSequenceId` at the final node (phase 2).
